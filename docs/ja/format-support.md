# 対応形式

| 形式 | 拡張子 | 図での表示 | 図からの編集 | 名前変更（F2） |
| --- | --- | --- | --- | --- |
| Turtle | `.ttl`, `.turtle` | ✅ | ✅ | ✅ |
| TriG | `.trig` | ✅ | — | — |
| N-Triples | `.nt` | ✅ | — | — |
| Notation3 | `.n3` | ✅ | — | — |
| RDF/XML | `.rdf`, `.owl` | ✅ | まず Turtle に変換 | — |
| JSON-LD | `.jsonld` | ✅ | まず Turtle に変換 | — |

## なぜ Turtle だけが編集可能なのか

図での編集を安全にソースファイルへ書き戻すには、変更対象が元のテキストの**正確な文字範囲**のどこに対応するかを知る必要があります。「このトリプルが変わった」という粒度ではなく、「この行の、この文字からこの文字まで」という粒度です。Turtle の文法（および本拡張機能が基盤とするトークナイザ）は、以下のような厄介なケースを含めてもこれを正しく扱えます。

- ドキュメントの途中でプレフィックスが再宣言され、前後で同じ `ex:` が異なる意味を持つ場合
- `@base` がドキュメントの途中で変わる場合
- 複数行にまたがる三重引用符の文字列リテラル
- 空白ノードのプロパティリスト（`[ ... ]`）や RDF コレクション（`( ... )`）

RDF/XML や JSON-LD で同じ保証を得るには、それぞれ専用の位置追跡パーサをゼロから書く必要があります（XML と JSON はトークン化の仕組みがまったく異なるため）。これははるかに大きな作業であり、微妙なバグが入り込む余地もはるかに大きくなります。同じレベルの確信を持てないまま書き戻し機能を提供するよりも、v1 では安全で十分にテストされた Turtle への経路だけに絞り、そのための明示的な入り口として「Turtle に変換」を用意しています。

## Turtle の中でも制限がある部分

有効な Turtle ファイルであっても、すべての部分が図から編集できるわけではありません。ノードが**点線の枠**（編集可能）で表示されるのは、以下に該当しない場合だけです。

| 状況 | どうなるか |
| --- | --- |
| 既存の `rdfs:label` が複数行（`"""..."""`）の文字列 | 図からは編集不可。テキストエディタで直接編集してください。 |
| 空白ノードのプロパティリスト（`[ ex:p ex:q ]`）や RDF コレクション（`( ex:x ex:y )`）の中にしか登場しないエンティティ | 図からは編集不可。 |
| 通常に書かれた Turtle ファイルのその他すべて | 編集可能。 |

これらは意図的に保守的にしてあります。推測して誤った内容を書き込むリスクを負うより、編集を提供しないほうを選びます。

## 安全性の保証

図からの編集も F2 によるリネームも、書き込む前に必ず同じチェックを経ます。

1. 提案される新しいテキストを計算する。
2. それを最初から再パースする。
3. 結果として得られる RDF グラフが、意図した変更とちょうど一致していることを確認する（リネームの場合は、古い識別子がどこにも残っておらず、新しい識別子が存在することも確認する）。
4. 3 を通過した場合にのみ、編集を適用する。

検証に失敗した場合は何も書き込まれず、理由を説明するエラーが表示されます。
