Background: what LLMs are missing

Tutorials 8 and 9 solve the same problem from two sides.

LLMs are good at writing. Put them to work, though, and you run into two problems.

Problem 1: answering from memory
YouWill the 12-speed cassette work with my 11-speed chain?
LLMYes, those generally work together.

The answer sounds right, but it comes from the model's memory. The model doesn't know what your own parts catalog says.

Problem 2: acting without the rules

The three signs above the truck mean "on route", "full" and "another depot".

YouPut this parcel on truck V-201.
AgentDone. I updated the data and put it on V-201.

Give an agent a tool that writes data, and it runs it without knowing your business rules. V-201 is on route, and may not have room either.

Both problems have the same cause: the LLM lacks correct information from outside itself. So you write down your company's knowledge as an ontology and hand it to the agent. An ontology describes what exists, how things connect, and what may be done, in a form a machine can read.

Tutorial 8: hand over the rules
Object Ontology
  • Defines objects such as shipments, vehicles and drivers, and the actions that change them.
  • Each action has preconditions, for example "the vehicle must be available".
  • The agent can change data only through these actions. The server rejects any call that breaks a precondition.

Tutorial 6 explains the idea; tutorial 8 runs it.

Tutorial 9: hand over the facts
Semantic Web (RDF / OWL)
  • Writes facts such as "cassette CS-R12 is compatible with chain CH-R12" as subject–predicate–object triples.
  • The agent writes a SPARQL query to look the facts up, and answers only from the rows that come back.
  • You can run the same query in the viewer to check it.

Tutorial 7 explains the idea; tutorial 9 runs it.

Where Claude Code fits

In both tutorials, the agent is Claude Code. It is an AI that runs in your terminal: it reads files and works with the tools and commands you allow. It asks for your permission before using a tool, so you can check every step it is about to take.

Let a dispatch agent change data

Object Ontology × MCP server × Claude Code

The setting

A harbor-city delivery company, 10:30 in the morning

Harbor City Delivery Ops is a fictional delivery company with two depots and three vehicles. Shipment S-5001 (120 kg) for Bayview Bakery was promised by 11:00. But its vehicle, V-101, has gone into maintenance, and the shipment is now delayed.

Weight already on board (bar length is the share of capacity)

The data lives in the ontology file delivery-ops.oont.yaml. The clock is fixed at 2026-05-12 10:30.

The problem

You want to tell the agent "S-5001 is late — fix it and tell the customer". But you don't want it to:

  • edit the data files directly to make things add up
  • put the shipment on a vehicle that is on route or based at another depot
  • make up a new arrival time and send it to the customer
  • leave no trace of what it did
The approach
  • The only way to change data is the actions defined in the ontology.
  • Each action's preconditions go into its tool description, so the model reads them before it calls.
  • Any call that still breaks a precondition is rejected by the server.
  • A person approves every write, and every result goes into an audit log.
How it works

The ontology becomes the agent's tools and rules

MCP (Model Context Protocol) is a standard way to give an AI tools. Once connected, Claude Code can call the tools an MCP server publishes.

Highlight 2

Two layers of protection, plus you

1
The model declines on its own

The preconditions are in the tool descriptions, so the model reads them before calling. In the video, it lists V-201's three problems, declines, and suggests V-102.

2
The server rejects the call

Even if the model gets it wrong, the server checks every precondition. It returns all the failed ones at once and changes nothing.

3
A person approves, and it's all recorded

You approve every write before it runs. Applied and rejected calls both go into the audit log.

The model usually gets it right. Stopping it reliably is the server's job.

Highlight 3 (section 5, not in the video)

Add a rule, and the server refuses until someone implements its check

1. Add a rule"The vehicle's driver must be on shift" becomes a precondition of assignVehicle.
2. Export againThe tool definitions update, so the model reads the new rule.
3. The server rejectsNo code checks the new rule yet, so it refuses even V-102, which qualifies. It fails safe.
4. Implement the checkA second Claude Code session, acting as the developer, adds one line and runs the tests.
5. It goes throughThe same request now succeeds, with no restart.

A rule can never silently drop out while the agent keeps working.

9

Answer from a parts catalog, with evidence

Semantic Web × SPARQL × Claude Code

The setting

The help desk of an online bike-parts shop

The shop has a fictional parts catalog, product-compatibility.ttl. It records, as triples, which parts fit which and which parts belong to what. A customer asks: "Will the 12-speed cassette fit the 11-speed chain I have now?"

The situation

What the catalog says about compatibility

Arrows point the way each fact is written in the file. compatibleWith is declared symmetric (if A fits B, B fits A), but the file writes each fact in one direction only.

The problem
  • Asked directly, an LLM may say "yes, it fits" from general knowledge instead of the catalog.
  • Even with the catalog in hand, it can miss facts written in only one direction.
  • It may turn "not recorded" into "not compatible".
  • Afterwards, it is hard for a person to check whether the answer was right.
The approach
  • Before answering, it always writes and runs SPARQL.
  • It answers only from the result rows and shows the queries it ran.
  • The pitfalls below are handed over as rules in CLAUDE.md.
  • A person runs the same query in the viewer's SPARQL panel and checks it on the diagram.
How it works

From a question to an answer you can check

npm run sparql uses the same engine (Comunica) as the viewer's SPARQL panel. Paste a query into the panel and you get the same rows, with the matching parts lit up on the diagram.

Highlight

Three pitfalls in LLM-written SPARQL

This example runs no reasoner. A reasoner fills in unwritten facts from definitions such as "symmetric" or "transitive". Without one, the query has to fill them in.

Symmetric properties Check both directions

"A fits B" may be written in one direction only. Check both, as in {A fits B} UNION {B fits A}.

Transitive properties Follow them with +

If the chain is part of the kit and the kit is part of the bike, the chain is part of the bike. Without the + in :partOf+, you find only the direct parts.

Reading false false means "not recorded"

An ASK that returns false means "the catalog doesn't say so", not "incompatible". Report what is recorded instead of drawing a conclusion.

Try it

The transitive trap: how many parts does the Trailfinder bike have?

Parts found: 7 
SELECT ?part WHERE { ?part (:partOf|^:hasPart)+ :trailBike }

Yellow marks the parts the query finds. With +, it follows the links into the kit and finds all 7. This is the query Claude Code writes at the end of the video.

Glossary

Terms used in the videos and tutorials

Ontology
A machine-readable description of what exists, how things connect, and what may be done.
Object Ontology
A way to describe a business as objects (shipments, vehicles…), links and actions. In this extension, a .oont.yaml file.
Action
A defined operation that changes data, such as assignVehicle (put a shipment on a vehicle).
Precondition
A condition an action must meet to run. If any one fails, the call is rejected. In the YAML: validations.
MCP server
A server that gives an AI its tools. In this example, it also checks and records every action.
Audit log / outbox
The record of every call, and the queue of side effects such as emails. Both live in state.json.
Semantic Web / RDF
A standard for writing facts as subject–predicate–object triples. The file format here is Turtle (.ttl).
SPARQL
The query language for RDF. ASK returns true or false; SELECT returns a table.
Reasoner
Software that fills in unwritten facts from definitions such as "symmetric" or "transitive". None runs here, so the queries fill them in.
GraphRAG
Having an LLM answer from the results of a graph search, instead of from memory.
CLAUDE.md
The project instructions file Claude Code reads when it starts.
